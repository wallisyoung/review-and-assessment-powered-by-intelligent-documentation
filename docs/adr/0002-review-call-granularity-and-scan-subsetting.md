# 審査呼び出しの粒度：逐項判定 ＋ 規則ごとのスキャン部分投入

17 条の比較ルールを審査する際、harness と同じ「全ルールを1呼び出しで一括判定（batch）」は採用せず、**既存の `review-workflow` per-item ループを再利用し、ルールごとに1呼び出し（逐項判定）** する。ただし各呼び出しには全スキャンではなく、**そのルールが参照する `文書タイプ` のスキャンのみ**を投入する。各ルールが必要とする `文書タイプ` は、`CheckList` 項目の显式メタデータ `requiredDocumentTypes` で宣言し（seed 時に設定）、毎回 `案件情報`(caseData) とともに渡す。

## なぜこの形か

- **コスト**: 全スキャンを毎回投入すると、ルールごとに最大4通（うち `登記簿謄本` は密で大きい）を17回再読みする。部分投入で大多数のルールは1通、最大2通で済む。
- **精度**: 関係ない書類を与えないことでコンテキストのノイズが減り、判定精度が向上する見込み。これは本プロジェクトの設計の売り（「必要なものだけ按需ロード」）であり、harness との比較の不公平にはあたらない。
- **再利用**: 既存の per-item レビューループ（`review-workflow` の pre→agent→post）をそのまま使え、新規の一括パスを書かずに済む。

## 考慮した選択肢

- **一括判定（harness 忠実）**: 全17ルール＋全スキャン＋案件情報を1呼び出しで処理し、出力を17件に分割する。harness との比較は最も apples-to-apples になるが、既存の per-item アーキテクチャから逸脱し、新規パスが必要。また部分投入の恩恵（コスト・精度）が得られないため不採用。
- **部分投入の導出方法**: (a) ルール本文から `文書タイプ` 名をテキスト正規マッチ、(b) `requiredDocumentTypes` の显式メタデータ。**(b) を採用**: seed 時に確実に設定でき、正規マッチの取りこぼしリスクがない。Phase 2 のテンプレート导入では (a) を自動導出のフォールバックとして使う。

## 帰結

- `CheckList` に `requiredDocumentTypes`（文字列配列）を追加。空/未設定時は安全側に倒して全スキャンを投入する。
- `登記完了証` は4種のうち規則が未策定の `文書タイプ`。特別扱いせず、他と同様に宣言・アップロード・投入可能な一等タイプとして扱う（demo の17ルールには未参照）。
- 本 ADR は ADR-0001（抽出戦略 A3）の上に乗る：抽出は多模态＋正規化ツール（A3a）、呼び出し構造は逐項＋部分投入。
