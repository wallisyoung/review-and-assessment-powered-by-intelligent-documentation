# 审查抽取策略：多模态直读 + 正规化工具（混合 A3）

不動産登記書類の整合性審査において、既存の AgentCore harness は**事前抽出済みの OCR データ（書類OCRデータ）**を入力としていた。本プロジェクトではこれを廃止し、スキャン PDF/画像を**多模态 LLM で直接読み**、案件情報 JSON と照合する。ただし LLM が誤りやすい正规化（和暦↔西暦変換、金額のカンマ区切り→数値、利率％の半角/全角）だけは **code-interpreter ツール**に委ね、決定論的に処理する（A3 ハイブリッド）。

## 考慮した選択肢

- **A1 端到端多模态のみ**：最速で、提案の売り（「PDF/画像を直接処理できる」）に直結する。しかし規則 7（乙区の自由文から日付抽出＋和暦変換＋最大登記順位）、規則 17（設定/抹消のペアリング）、規則 16（日付論理）など、抽出が難しい規則の精度リスクが大きい。
- **A2 先抽出→後比較**：Pass1 で各書類のフィールドを構造化抽出（≈書類OCRデータ を再構築）、Pass2 で案件情報と比較（厳密一致はコード化可能）。比較は安定するが工数が大きく、端到端の売りを薄め、harness の OCR 段を再実装することになる。
- **A3 ハイブリッド（採用）**：多模态で読み、**正规化のみ**をツール化する。売り（端到端）を保ちつつ、最大の精度リスクである正规化を決定論で潰す。Demo の目的（精度を測る）に対し、最も費用対効果が高い。

## 帰結

- `書類OCRデータ` は本プロジェクトのモデルに登場しない（概念を廃止）。
- `review-item-processor` の既存 `code_interpreter` ツール（`tools/code_interpreter.py`）と `ToolConfiguration.codeInterpreter` を正規化用途で有効化する方向で検討する。
- 正規化ヘルパーの対象範囲（全規則 vs 正規化重視規則のみ）・比較をコードで行うか LLM で行うかは、後続の設計で確定する。
